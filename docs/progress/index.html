DEVELOPMENT MILESTONE / 8 SEPTEMBER 2026

One response, two valid ways to close it

HTTPX is a Python HTTP client. Our first task reads only the start of a response, then releases it while keeping the client open. The new contracts define three distinct roles:

  • The verifier checks whether the evidence supports the guidance drafted by the layer.
  • The checker questions the agent’s plan and actions while it works, and decides whether it can proceed.
  • The judge assesses the finished work against the reference evidence after the attempt ends.

Both the context-managed solution and explicit closure in a finally clause passed. Missing closure and closure only on the normal path failed; empty-body tests alone would have missed those errors. The record includes the exact inputs, scripted decisions and observed behaviour.

The decisions in this trace are scripted, not model outputs. File-broker checks passed, but they do not establish container isolation. Next we will build isolated role execution and enforce the review checkpoints; independent qualification will use different examples.

THE WHOLE PROCESS

Where we are in the process

  1. Decide what the experiment should prove

    Complete

    We reviewed the playbook and defined the question: does preparing guidance help an agent make a later change, and does checking its use add further value? Owner approval remains outside this technical test.

  2. Find suitable cases in real projects

    Complete

    We reviewed 84 candidate records across four projects. We selected 52 for further development, covering 39 groups of related decisions. They still need working tasks and reliable scoring before they can become experiments.

  3. 3

    Build and check the experimental procedure

    Next

    Component contracts and the first scripted example now exist. Next implement isolated role execution and checkpoint enforcement, then build further cases and validate the components on separate material. This preparation is not complete.

  4. 4

    Run a small trial to test the setup

    Not started

    Compare the three ways of working on a small set of tasks. Check whether the tasks are useful, the scores are reliable and the costs are recorded. Material used to improve the setup will stay out of the main trial.

  5. 5

    Fix the rules for the main trial

    Not started

    Before seeing the main results, choose the final cases, number of runs, scoring rules and resource limits. Record how much improvement would justify the added work and how we will analyse related cases.

  6. 6

    Run the main comparison

    Not started

    Run the agreed comparisons in separate controlled environments. Keep unsuccessful and unfinished attempts in the record, and assess the work independently.

  7. 7

    Use the results to revise the playbook

    Not started

    Explain where the layer helped, where it did not and what it cost. If the result is uncertain, say so. Keep the conclusions within what these projects and tasks can establish.

Can we enforce the contracts in isolated runs?

The first contracts and scripted case exist. Next build immutable role dispatch, validate structured outputs, test filesystem and network restrictions, and enforce the checkpoints and stop decisions.

Which decisions should the first trial cover?

Choose cases from several repositories, including rules the code supports, legitimate exceptions, disagreements with documentation and questions the code cannot answer.

03

Does the proposed checking procedure work for the pilot cases?

Start with a plan check before editing and checks on submitted code changes. Require a new plan for a changed approach, and allow at most two correction rounds per checkpoint. Build and validate this proposal before treating it as the trial procedure.

Open
04

How do we make the three conditions comparable?

Compare direct work from the sources, prepared guidance alone, and the same guidance with interaction. Give them comparable resources and count the cost of preparing guidance and checking the work.
