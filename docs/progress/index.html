DEVELOPMENT MILESTONE / 8 SEPTEMBER 2026

One response, two valid ways to close it

HTTPX is a Python HTTP client. The first task reads only the start of a response, then releases it while keeping the client open. The new contracts define three distinct roles:

  • The verifier checks whether the evidence supports the guidance drafted by the layer.
  • The checker questions the agent’s plan and actions while it works, and decides whether it can proceed.
  • The judge assesses the finished work against the reference evidence after the attempt ends.

Both the context-managed solution and explicit closure in a finally clause passed. Missing closure and closure only on the normal path failed; empty-body tests alone would have missed those errors. The record includes the exact inputs, scripted decisions and observed behaviour.

The decisions in this trace are scripted, not model outputs. File-broker checks passed, but they do not establish container isolation. The next implementation task is isolated role execution, containment testing and enforced review checkpoints; independent qualification will use different examples.

TECHNICAL READINESS

What is built and what still needs validation

H04 exports hashed role packs and has component contracts. The project-instruction audit and historical case packs remain to be prepared.

Runner and review checkpoints

The rehearsal checks correction limits, stop states and known lifecycle changes. Isolated dispatch, full record validation, general plan-change detection and enforced execution pauses remain to be built.

Isolation and model gateway

Next: select the execution boundary and controller interfaces, build and test the model-free runner, then qualify components on different case families before authorised model comparisons.

THE WHOLE PROCESS

Current position in the process

  1. Decide what the experiment should test

    Complete

    The playbook review established the question: does preparing guidance help an agent make a later change, and does checking its use add further value? Owner approval remains outside this technical test.

  2. Find suitable cases in real projects

    Complete

    The inventory review covered 84 candidate records across four projects. Of these, 52 advance to development, covering 39 groups of related decisions. They still need working tasks and reliable scoring before they can become experiments.

  3. 3

    Build and check the experimental procedure

    Next

    Component contracts and the first scripted example now exist. Next select and test the isolation architecture, then build further cases and qualify the assessment roles on separate material. This preparation is not complete.

  4. 4

    Run a small trial to test the setup

    Not started

    The pilot will compare the three ways of working on a small set of tasks to check task quality, scoring reliability and cost records. Material used to improve the setup will stay out of the main trial.

  5. 5

    Fix the rules for the main trial

    Not started

    The final cases, number of runs, scoring rules and resource limits must be fixed before the main results are seen. This includes the improvement needed to justify the added work and how related cases will be analysed.

  6. 6

    Run the main comparison

    Not started

    The agreed comparisons will run in separate controlled environments. Unsuccessful and unfinished attempts remain in the record, and the work is assessed independently.

  7. 7

    Use the results to revise the playbook

    Not started

    The findings will explain where the layer helped, where it did not and what it cost. Conclusions must reflect uncertainty and stay within what these projects and tasks can establish.

DECISIONS STILL TO MAKE

Before the pilot can run

The remaining decisions are recorded below. The plan now defines the assessment roles, cost allocation and failure handling. The settings and evidence below still need to be completed at their stated gates. None is implied by publishing the design.

01

Before any model calls: can the runner enforce the boundaries?

Select the isolation technology and permitted interfaces, then demonstrate input restrictions, review pauses, stop enforcement, bounded model access and resistance to forbidden direct and indirect routes. Record the configuration and probe results.

02

Before selecting runnable cases: is each assessment defensible?

Pin each task’s starting revision and applicable rules, check its valid and invalid solutions, audit disclosures and actual AGENTS.md files, and separate historical tasks from authored examples. The inventory snapshots alone do not establish historical eligibility.

Open
03

Before qualification: what must each assessor pass?

Build separate development and validation families with justified expected assessments. Fix role-specific instructions, models, error limits, coverage, sample size and acceptance rules before opening validation results. The verifier must not score its own success.

Open
04

Before the pilot: are the run settings complete?

Fix preparation and revision limits, total method budgets, guidance reuse assumptions, review triggers, treatment order, scoring, retries and the audit sample. Preparation consumes part of each guidance group’s allowance. All required components must have passed qualification.

Open
05

Before confirmation: what result would justify the work?

Use pilot feasibility evidence to fix the primary comparison and endpoint, worthwhile benefit and cost limit, treatment of related cases, repetitions and sample-size justification. Keep tuning families out of confirmation.
