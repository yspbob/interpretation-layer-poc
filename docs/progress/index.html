DEVELOPMENT MILESTONE / 8 SEPTEMBER 2026

One response, two valid ways to close it

HTTPX is a Python HTTP client. The first task reads only the start of a response, then releases it while keeping the client open. The new contracts define three distinct roles:

  • The verifier checks whether the evidence supports the guidance drafted by the layer.
  • The checker questions the agent’s plan and actions while it works, and decides whether it can proceed.
  • The judge assesses the finished work against the reference evidence after the attempt ends.

Two solutions released the response correctly. One used a context manager, which handles cleanup automatically. The other closed the response explicitly in a finally clause, so cleanup would still happen after an error.

The checks caught code that never closed the response and code that closed it only when nothing went wrong. Testing an empty response alone would have missed those mistakes. The record includes the exact inputs, scripted decisions and observed behaviour.

The review decisions were written in advance. They were not made by a model. Checks on which files the program could request passed, but they do not establish that a container can isolate an agent.

The next implementation work is to run roles separately, test their access restrictions and enforce review pauses. Independent tests of the judges will use different examples.

TECHNICAL READINESS

Technical details behind the current status

Pilot scope clarified

Phase 1 will ask agents to repeat real changes from one selected public project. Each task needs clear requirements and supporting evidence. A model may already know that code, so the results cannot prove it discovered every rule from unfamiliar files.

If the evidence cannot settle a central requirement, that case stays out of scoring. We assess the historical implementation too, because it may contain mistakes.

Case selection and independent tests of the judges remain unfinished. Zero model comparisons have run. Read the scope and limitation.

DECISIONS STILL TO MAKE

Decisions needed for this phase

The plan describes how the experiment should work. Before it can run, the controls must be built and tested, the cases and judges must be checked, and the settings below must be fixed. Publishing the design does not complete those steps.

01

Can the selected machine enforce the boundaries?

Build and test the proposed setup on the one machine chosen for this trial. Show that it restricts inputs, enforces pauses and stops, and controls model access. Test attempts to use forbidden direct and indirect routes. Record the exact setup and results.

Open
02

Before selecting runnable cases: is each assessment defensible?

Identify the code and rules as they stood when each historical task began. Check valid and invalid solutions, inspect project instructions and look for files that reveal hidden answers. Keep authored examples separate from historical tasks. The inventory alone does not complete these checks.

Open
03

Before qualification: what must each assessor pass?

Build separate development and validation families with justified expected assessments. Fix instructions for each role, models, error limits, coverage, sample size and acceptance rules before opening validation results. The verifier must not score its own success.

Open
04

Before the pilot: are the run settings complete?

Use the development calibration to choose the spending allowance, then fix preparation and correction limits. Record which tasks share each guide and how its cost is divided. Also fix when reviews happen, the order of groups, scoring and retry rules, and which scores will be audited. Every required component must have passed its qualification tests.

Open
05

What will the phase report need to show?

Record the tested scope, control results, task outcomes, failures, costs and uncertainty. Use that report to decide whether to proceed, revise or stop. A favourable result is not a condition for completing the report.
