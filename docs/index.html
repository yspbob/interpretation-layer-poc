THE FIRST TRIAL / PHASE 1 OF 3

Can we reconstruct the project’s rules?

First, ask the interpretation layer to turn project evidence into guidance. Then check whether that guidance is accurate, explains its limits and covers the decisions we expected it to find.

The interpretation layer is the mechanism proposed in Chapter 4 of the AI Engineering Playbook. It should help agents understand the rules behind a system. Before testing whether it helps them write code, we need to see what it actually produces.

See progress and the next step
THE RESULT OF THIS PHASE

A guide we can inspect, with evidence for its claims and an independent assessment.

The report will show correct rules, missing rules, unsupported claims and unresolved questions. A fluent explanation or a list of citations will not be enough.
Testing the guide in a coding task comes in Phase 2.
01
THE WORK IN THIS PHASE

From project evidence to an assessed guide

  1. 1

    Choose the evidence and establish what it supports

    Select one repository and a few different kinds of decisions. For each, establish the applicable rule, exceptions and any uncertainty using project records and reproducible behaviour.

    Prepare separate files for the layer and for assessment. The layer receives only its permitted project evidence. The assessment record stays hidden.

  2. 2

    Ask the drafter to prepare guidance

    The drafter is the part of the interpretation layer that proposes rules. It explains what each rule means, where it applies, what supports it and where an exception or uncertainty remains.

    It does not receive a later coding task or the assessment answers. We keep its original draft so that mistakes remain visible even if they are corrected later.

  3. 3

    Check the draft against its evidence

    A separate verifier checks the drafter’s claims. It can accept a supported claim, request a correction or leave it unresolved. Any permitted revisions follow limits fixed before the run.

    Save both the draft and the accepted guide, together with the verifier’s decisions. Acceptance means that the verifier found evidence support. It is not approval from a project owner.

  4. 4

    Assess the guidance independently

    A separate assessment uses the hidden reference evidence to examine the draft, the accepted guide and the verifier’s decisions. The verifier cannot judge its own success.

    Check what the guide got right, what it missed and what it asserted without support. Also check whether the verifier accepted a bad claim or rejected a valid one. Record preparation time, cost and failed attempts.

WHAT WE WILL HAVE

A result we can examine before building more.

A versioned guide, its claim evidence, the original draft, the verifier’s decisions and an independent assessment. The report includes omissions, failures, uncertainty and preparation costs.

The decision at the end

Decide whether the guide is defensible enough to test in a coding task, whether preparation needs repair or whether to stop. A positive result is not required to finish this phase.

This phase can establish the quality of the guidance in the tested cases. It cannot show that the guidance improves code or pays for itself.

02
KEEPING THE TEST CREDIBLE

Build the controls this phase actually uses

The drafter, verifier and independent assessor need separate contexts and explicit access boundaries. We must record what each received and prevent hidden assessment material from reaching the working roles.
