## Purpose and current position

We are testing whether the interpretation layer proposed in [chapter 4 of the AI Engineering Playbook](https://yspbob.github.io/AI-Playbook/AI_Engineering_Playbook.html#4-the-interpretation-layer) produces useful, defensible guidance and improves subsequent engineering work. A positive result would support the mechanism in the tested situations, not prove that every organisation needs it.

The agreed first pilot compares the methods on evidence-backed historical tasks from public projects, with possible prior model familiarity. It does not establish inference entirely from unseen code. Private rule-changing variants are optional later work, not a pilot prerequisite.

The redesigned POC is still being prepared. There are **zero blinded model runs**. Component contracts and a scripted development trace now exist; no model verifier, interactive checker or final judge has been exercised or qualified under the current protocol.

## Decisions to preserve

- No accessible project owner is available. The technical experiment uses published references and reproducible behaviour; it cannot certify that newly inferred rules express an owner's unrecorded intentions.
- Separate deriving guidance from code from reading guidance in documentation. Record the provenance and qualifications of individual claims.
- Use the actual applicable AGENTS.md files from each backtest’s starting revision in all matched groups; record hashes, scope or absence. If the files state the target rule, classify the case as documentation-visible rather than strip real instructions or claim code inference.
- Compare DIRECT (sources and ordinary review), GUIDE (the same plus frozen guidance) and INTERACT (the same guidance plus structured consultation and checking). Match checkpoints, correction opportunities and resource limits; include preparation and review costs.
- Use the same review-trigger policy and correction limits across groups, with initial and final review plus checks during execution. Different approaches can cause different intermediate checks. The working proposal allows two correction rounds per checkpoint. Necessary unresolved decisions and exhausted attempts stop and remain outcomes; unrelated unknowns do not automatically stop valid work.
- Assess historical and agent implementations for task correctness and guardrail compliance under the same independently established criteria. Credit avoided historical violations when the task is still correct; preserve legitimate exceptions and unresolved evidence. Exact points and weighting remain open. H04 has not implemented or validated this historical comparison.
- Separate treatment decisions from later assessment. Qualify verification, runtime review and independent assessment of guidance, code and interventions for their actual roles and inputs. The verifier cannot score its own success. Use defensible expected assessments, legitimate alternatives and separate development/qualification/confirmation families. Exact numerical gates remain open.
- Containment is required before model calls: isolate each role and run, prevent communication through shared writable services, minimise and test all exposed capabilities, mediate permitted exchanges externally, protect evaluation and enforcement, and test direct and indirect escape paths. Stop and retain affected runs on failure. Section 8 of the plan and the contracts addendum specify the requirements; they remain unimplemented and unvalidated.
- Isolation must record the actual files, tool access and network boundaries. It does not erase prior model knowledge of public sources. The first pilot acknowledges prior familiarity. Private rule-changing variants are optional later work and require independently justified validation; keep input audits and runtime isolation in force.
- The public candidate inventory is investigator-visible preparation material. It is not a sealed holdout. Never run a purported blind drafter in the conversation that has already seen its answers.
- Keep substantive website changes synchronized with the plan. Clearly distinguish a proposal, an agreed next step, implementation, validation and a frozen protocol.
