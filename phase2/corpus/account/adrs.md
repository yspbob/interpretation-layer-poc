# account — retro-ADRs (NetBox ea4c205)

## ADR-A1: "Current user" views live in their own `account` app, separate from the `users` admin app

**Context.** NetBox has an administrative `users` app (users, groups, permissions, tokens for any user) mounted at `/users/`. Self-service pages (profile, preferences, own tokens) need different URL names, templates and authorisation from the admin CRUD views [code:netbox/netbox/urls.py:32] [code:netbox/users/views.py:15-38].

**Decision.** A separate Django app `account` was created in a single commit on 2023-07-31, mounted at `/user/` with URL namespace `account`; the unauthenticated `LoginView`/`LogoutView` are defined there but mounted at the project root (`/login/`, `/logout/`) [fg:churn:account] [fg:churn:account.urls] [code:netbox/account/urls.py:6] [code:netbox/netbox/urls.py:7] [code:netbox/netbox/urls.py:20-22] [code:netbox/netbox/urls.py:38].

**Consequences.** The app is thin: it owns views, one table and one proxy model, but borrows forms from `users` and tables/models from `extras` and `core`, so most changes to a profile tab are cross-app edits [code:netbox/account/views.py:21-33] [fg:imports:account.views->users]. Other apps couple to it by URL name rather than import: `extras` models and views redirect to `account:notifications`/`account:subscriptions`, the user menu links five `account:` names, and `settings.LOGIN_URL` hard-codes `/login/` [code:netbox/extras/models/notifications.py:91] [code:netbox/extras/views.py:510] [code:netbox/templates/inc/user_menu.html:39-51] [code:netbox/netbox/settings.py:524]. Renaming a URL name here breaks `extras` and templates without any import edge flagging it [fg:subsystems:account] [fg:imports:users.tables->account.tables].

## ADR-A2: Self-service tokens are a proxy model, not a separate table or the raw `Token`

**Context.** `register_model_view()` and `get_model_urls()` key registered views on `(app_label, model_name)`, and `get_absolute_url()` is a per-model method. Using `users.Token` directly in `account` would collide with the admin views registered on `Token` and would link every token to `users:token` [code:netbox/utilities/views.py:305-318] [code:netbox/utilities/urls.py:24-32] [code:netbox/users/models/tokens.py:81-82].

**Decision.** `account.models.UserToken` is a `proxy = True` subclass of `Token` with its own `get_absolute_url()` (`account:usertoken`) and `_netbox_private = True`; its migration creates no columns and depends only on the `users` squash [code:netbox/account/models.py:6-17] [code:netbox/account/migrations/0001_initial.py:14-26]. Detail views are registered against `UserToken`, giving the namespace `account:usertoken`, `account:usertoken_edit`, `account:usertoken_delete` [code:netbox/account/views.py:341-369] [code:netbox/account/urls.py:18].

**Consequences.** Because `get_permission_for_model()` resolves proxies to the concrete model, no new permissions exist: the account views check `users.{view,add,change,delete}_token`, the same permissions the admin views check [code:netbox/utilities/permissions.py:24-27] [code:netbox/netbox/views/generic/object_views.py:187-190]. The `_netbox_private` flag is inert in practice: it is read only by `register_models()`, which every other app calls from its `AppConfig.ready()`, and `account` has no `apps.py` [code:netbox/netbox/models/features.py:651-658] [code:netbox/users/apps.py:12] [fg:modules:account]. The admin `TokenTable` and `TokenForm` subclass the self-service `UserTokenTable`/`UserTokenForm` (adding a `user` column/field), so the proxy's presentation is the base for the admin's, not the reverse [code:netbox/users/tables.py:16-26] [code:netbox/users/forms/model_forms.py:153-163].

## ADR-A3: Ownership of tokens, bookmarks, notifications and subscriptions is enforced by default constrained permissions, not by hard-coded checks in the generic views

**Context.** The generic `ObjectEditView`/`ObjectDeleteView`/`ObjectListView` gate on model permissions and restrict their queryset through `ObjectPermission` constraints; they have no notion of "the current user's rows" [code:netbox/utilities/views.py:97-110] [code:netbox/netbox/views/generic/base.py:24-26].

**Decision.** `DEFAULT_PERMISSIONS` grants every user view/add/change/delete on `extras.bookmark`, `extras.notification`, `extras.subscription` and `users.token`, each constrained to `{'user': '$user'}`, and `ObjectPermissionMixin.get_all_permissions()` merges those in for every authenticated user [code:netbox/netbox/settings.py:96-117] [code:netbox/netbox/authentication/__init__.py:86-92]. The account views therefore use the unmodified generic views with `objects.all()` querysets for edit/delete and only stamp `obj.user = request.user` on create [code:netbox/account/views.py:355-363] [code:netbox/account/views.py:367-369]. The docs state the intent: self-service token management "can be disabled by overriding the `DEFAULT_PERMISSIONS` configuration parameter" [code:docs/integrations/rest-api.md:636].

**Consequences.** Operators can switch off self-service by editing configuration, with no code change [code:netbox/netbox/settings.py:96]. The read-only tab views do not rely on this and filter on `request.user` explicitly, so the two halves of the subsystem can diverge if `DEFAULT_PERMISSIONS` is customised: a user might see their tokens but be unable to add one [code:netbox/account/views.py:330] [code:netbox/account/views.py:345] [code:netbox/account/views.py:356]. The test configuration sets `DEFAULT_PERMISSIONS = {}`, and the `extras` tests that reuse the account list URLs disable their "with permission" cases, so the default-permission path is not exercised by the suite [code:netbox/netbox/configuration_testing.py:44] [code:netbox/extras/tests/test_views.py:697-701].

## ADR-A4: Login is a hand-written `View`, not Django's `LoginView`

**Context.** Beyond authenticating, NetBox login must list SSO backends (including one entry per SAML IdP), avoid a database write in maintenance mode, backfill a missing `UserConfig`, and set a language cookie from user preferences [code:netbox/account/views.py:68-86] [code:netbox/account/views.py:109-113] [code:netbox/account/views.py:120-124] [code:netbox/account/views.py:128-135].

**Decision.** `LoginView(View)` uses Django's `AuthenticationForm` and `auth_login()` but implements `get`/`post`/`redirect_to_next` itself, wrapping `dispatch` in `sensitive_post_parameters('password')` [code:netbox/account/views.py:40-48] [code:netbox/account/views.py:88-104] [code:netbox/account/views.py:148-159]. In maintenance mode it disconnects Django's `update_last_login` receiver before calling `auth_login()` [code:netbox/account/views.py:111-116].

**Consequences.** The `next` parameter is validated with `safe_for_redirect()` and falls back to `home`; unsafe values are logged with line breaks stripped [code:netbox/account/views.py:150-159]. The `user_logged_in.disconnect(...)` call is process-global and the only reference to `update_last_login` in the tree is this disconnect (there is no matching `connect`), so once a login occurs during maintenance mode, `last_login` is not updated by later logins in that worker even after maintenance mode is cleared [code:netbox/account/views.py:8] [code:netbox/account/views.py:111-113]. `LoginView` is the highest-churn code in the subsystem's only high-churn module (22 commits, 5 authors), which is where feature additions to authentication have landed [fg:churn:account.views].

## ADR-A5: The UI language cookie is bound to the session lifetime

**Context.** Language preference is stored in `UserConfig` (`locale.language`) but Django's locale middleware reads a cookie [code:netbox/account/views.py:129] [code:netbox/users/forms/model_forms.py:59-64].

**Decision.** The cookie is written on login and on preference save with `max_age=request.session.get_expiry_age()` and `secure=settings.SESSION_COOKIE_SECURE`, cleared when the preference is emptied, and deleted on logout alongside `session_key` [code:netbox/account/views.py:130-135] [code:netbox/account/views.py:228-236] [code:netbox/account/views.py:176-179].

**Consequences.** The cookie cannot outlive the session, and a preference change takes effect without re-login; any new place that starts a session or changes the preference must repeat the same cookie handling, as there is no shared helper for it [code:netbox/account/views.py:130-135] [code:netbox/account/views.py:229-234].
