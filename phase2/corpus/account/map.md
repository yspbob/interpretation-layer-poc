# account — subsystem map (NetBox ea4c205)

## What it is

`account` is the "current user" app: web login/logout, the profile tab set (profile, preferences, password, bookmarks, notifications, subscriptions) and self-service API-token management. It is 469 lines of code across six real modules plus an empty package `__init__`, has no tests of its own, no API, no GraphQL, no signals, no forms and no filtersets; it borrows those from `users`, `extras` and `core` [fg:subsystems:account] [fg:modules:account] [code:netbox/account/views.py:21-33].

It is mounted at `/user/` by the project URLconf, while its two unauthenticated views (`LoginView`, `LogoutView`) are imported directly by `netbox.urls` and mounted at top-level `/login/` and `/logout/` [code:netbox/netbox/urls.py:7] [code:netbox/netbox/urls.py:20-22] [code:netbox/netbox/urls.py:38] [fg:imports:netbox.urls->account.views].

## Modules by role

- **Models** — `account.models` (18 loc) defines a single proxy model `UserToken(Token)` with `proxy = True`, `_netbox_private = True`, and `get_absolute_url()` pointing at `account:usertoken` rather than the concrete model's `users:token` [fg:symbols:account.models:UserToken] [code:netbox/account/models.py:6-17] [code:netbox/users/models/tokens.py:81-82].
- **Migrations** — one migration, `0001_initial`, creating the proxy over `users.token` with a dependency on `users.0002_squashed_0004` [fg:symbols:account.migrations.0001_initial:Migration] [code:netbox/account/migrations/0001_initial.py:10-26].
- **Tables** — `account.tables.UserTokenTable(NetBoxTable)` renders key, write flag, timestamps, allowed IPs and an actions column whose extra copy button is gated on `settings.ALLOW_TOKEN_RETRIEVAL` [fg:symbols:account.tables:UserTokenTable] [code:netbox/account/tables.py:15-19] [code:netbox/account/tables.py:48-51].
- **Views** — `account.views` (370 loc, 12 classes) is where nearly all behaviour lives: `LoginView`, `LogoutView`, `ProfileView`, `UserConfigView`, `ChangePasswordView`, `BookmarkListView`, `NotificationListView`, `SubscriptionListView`, `UserTokenListView`, `UserTokenView`, `UserTokenEditView`, `UserTokenDeleteView` [fg:modules:account.views] [fg:symbols:account.views:LoginView] [fg:symbols:account.views:UserTokenDeleteView].
- **URLs** — `account.urls` (`app_name = 'account'`) is the only entry point recorded for the subsystem; it maps the seven tab views plus `api-tokens/add/` explicitly and delegates `api-tokens/<pk>/` to `get_model_urls('account', 'usertoken')` [fg:entrypoints:account.urls] [code:netbox/account/urls.py:6-20].
- **Templates** — the account views render `templates/account/*.html` (a `base.html` tab bar plus one page per tab) and `templates/login.html`; the templates are outside the slice but are the concrete consumers of the `active_tab` context key set by every tab view [code:netbox/templates/account/base.html:4-30] [code:netbox/account/views.py:199-202].
- **Absent roles** — there is no `apps.py`, so `register_models()` is never invoked for `account`; the `_netbox_private` flag on `UserToken` is therefore only read if something else registers the model, and nothing in the tree does [fg:modules:account] [code:netbox/netbox/models/features.py:641-658] [code:netbox/users/apps.py:12].

## Dependents (inbound)

Only two import edges point into `account`, and no string references (no ForeignKey targets a model in this app) [fg:imports:netbox.urls->account.views] [fg:imports:users.tables->account.tables] [fg:subsystems:account].

- `netbox.urls` imports `LoginView`/`LogoutView` and includes `account.urls`; this is the only place the app is wired into request routing [code:netbox/netbox/urls.py:7] [code:netbox/netbox/urls.py:21-22] [code:netbox/netbox/urls.py:38].

## Authorisation model

The tab views mix two mechanisms. `ProfileView`, `UserConfigView`, `ChangePasswordView`, `UserTokenListView` and `UserTokenView` are plain `View`s behind Django's `LoginRequiredMixin` and scope data by filtering on `request.user` themselves [code:netbox/account/views.py:188-194] [code:netbox/account/views.py:327-331] [code:netbox/account/views.py:342-345].

`BookmarkListView`, `NotificationListView` and `SubscriptionListView` combine `LoginRequiredMixin` with `generic.ObjectListView`, so they additionally require `extras.view_<model>` via `ObjectPermissionRequiredMixin` and then override `get_queryset()` to the current user's objects [code:netbox/account/views.py:280-285] [code:netbox/netbox/views/generic/bulk_views.py:64-65] [code:netbox/utilities/views.py:97-110].

`UserTokenEditView` and `UserTokenDeleteView` have **no** `LoginRequiredMixin` and use `UserToken.objects.all()`; their protection is entirely the generic view's permission check, which resolves through the proxy to the concrete model (`users.add_token`, `users.change_token`, `users.delete_token`) and restricts the queryset by the user's `ObjectPermission` constraints [code:netbox/account/views.py:354-369] [code:netbox/utilities/permissions.py:17-27] [code:netbox/netbox/views/generic/object_views.py:181-190]. Those permissions are granted to every user, constrained to `{'user': '$user'}`, by the default `DEFAULT_PERMISSIONS` setting, which `ObjectPermissionMixin.get_all_permissions()` merges in; the testing configuration sets `DEFAULT_PERMISSIONS = {}` [code:netbox/netbox/settings.py:112-117] [code:netbox/netbox/authentication/__init__.py:86-92] [code:netbox/netbox/configuration_testing.py:44]. Login itself is only enforced on those two views when `LOGIN_REQUIRED` is true (`ConditionalLoginRequiredMixin`); ownership on create is set by `alter_object()` [code:netbox/utilities/views.py:32-39] [code:netbox/account/views.py:360-363].

## Where change concentrates

`account.views` carries 22 of the subsystem's 32 commits and all five of its authors, with activity from the app's creation (2023-07-31) through 2025-06-03; every other module has one or two commits [fg:churn:account.views] [fg:churn:account.models] [fg:churn:account.tables] [fg:churn:account.urls]. The migration was touched once after creation (2025-03-07), consistent with the users-app squash it now depends on [fg:churn:account.migrations.0001_initial] [code:netbox/account/migrations/0001_initial.py:10-12]. An engineer changing this subsystem should expect the blast radius to be in `views.py` and in the `users`/`extras` artifacts it borrows, not in the model or migration [fg:churn:account.views] [fg:imports:account.views->users].
