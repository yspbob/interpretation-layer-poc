# netbox (core package) — retro-ADRs

## ADR-1: Cross-cutting model features are abstract mixins, discovered by introspection

- **Context.** Tags, custom fields, change logging, journaling, bookmarks, contacts, jobs and synced data must attach to dozens of models across ten apps and to plugin models without per-app re-implementation. [fg:subsystems:netbox] [fg:imports:dcim.models.devices->netbox.models.features]
- **Decision.** Each feature is an abstract `models.Model` mixin in `models/features.py`; base classes (`NetBoxModel`, `OrganizationalModel`, `NestedGroupModel`) stack them via `NetBoxFeatureSet`; `register_models()` derives a model's feature set by `issubclass()` against `FEATURES_MAP` and records it in `registry['model_features']`, attaching feature views (changelog, journal, jobs, sync, contacts) at the same time. [code:netbox/netbox/models/features.py:618-638] [code:netbox/netbox/models/features.py:641-692] [code:netbox/netbox/models/__init__.py:25-47]
- **Consequences.** Some mixins are empty markers whose only purpose is registry classification (`CustomLinksMixin`, `ExportTemplatesMixin`, `EventRulesMixin`); code elsewhere tests capability with `hasattr(obj, 'snapshot')` or `hasattr(model, 'custom_fields')` rather than type checks; plugin models get identical treatment because `PluginConfig.ready()` calls the same function. [code:netbox/netbox/models/features.py:314-346] [code:netbox/netbox/models/features.py:475-481] [code:netbox/netbox/plugins/__init__.py:100-104]
- **Evidence.** `models.features` is the fourth most-imported module in the package (37 importers) and has 77 commits by 11 authors, the highest churn of any model module. [fg:imports:extras.models.customfields->netbox.models.features] [fg:churn:netbox.models.features]

## ADR-2: Object-level permissions are enforced by queryset restriction plus post-write verification

- **Context.** `ObjectPermission` grants actions on object types with optional constraints; Django's `has_perm(obj)` is per-instance and cannot express "which objects may this user see or create". [code:netbox/netbox/authentication/__init__.py:78-107] [fg:imports:netbox.authentication->users.models]
- **Decision.** Every read path applies `queryset.restrict(user, action)` (`BaseViewSet.initial`, generic views, feature views, GraphQL `get_queryset`, the HTMX selector); every write path saves inside `transaction.atomic()` and then checks the saved object is still matched by the restricted queryset, raising `PermissionsViolation` or `ObjectDoesNotExist` to roll the transaction back. [code:netbox/netbox/api/viewsets/__init__.py:40-46] [code:netbox/netbox/graphql/types.py:28-34] [code:netbox/netbox/views/generic/object_views.py:284-291] [code:netbox/netbox/api/viewsets/mixins.py:167-180]
- **Consequences.** The "save, verify, raise" block is repeated in `ObjectEditView`, `ComponentCreateView`, all bulk views and both API `perform_*` hooks; backend `has_perm(obj)` checks the database row, not the instance; `DEFAULT_PERMISSIONS` constraints are merged as if they were `ObjectPermission` rows. [code:netbox/netbox/views/generic/bulk_views.py:684-690] [code:netbox/netbox/authentication/__init__.py:142-151] [code:netbox/netbox/settings.py:96-99]
- **Evidence.** `test_authentication` (581 lines, 28 commits) carries the `ObjectPermissionAPIViewTestCase`; `views/generic/bulk_views.py` and `object_views.py` are the two most-changed modules after `settings.py`. [fg:modules:netbox.tests.test_authentication] [fg:churn:netbox.views.generic.bulk_views]

## ADR-3: A single fixed-key `Registry` is the extension bus

- **Context.** Apps and plugins need to contribute search indexes, data backends, menus, table columns, event types, system jobs, denormalised fields, request processors, GraphQL schemas and template extensions. [code:netbox/netbox/plugins/__init__.py:28-36] [fg:imports:utilities.views->netbox.registry]
- **Decision.** One module-level `Registry` (a `dict` subclass that refuses new or deleted keys) holds thirteen named stores; every extension point is a `register_*` helper or decorator writing into one store, and the registry is exposed to templates through a context processor. [code:netbox/netbox/registry.py:5-38] [code:netbox/netbox/context_processors.py:35-41] [code:netbox/netbox/search/__init__.py:143-151]
- **Consequences.** Adding a new kind of extension requires editing `registry.py`; stores are populated during `AppConfig.ready()` or at import (`settings.py` writes `registry['plugins']['installed']` while building `INSTALLED_APPS`), so import order matters; `CoreMiddleware` iterates `registry['request_processors']` on every request. [code:netbox/netbox/settings.py:852-853] [code:netbox/netbox/middleware.py:38-45] [code:netbox/netbox/tests/test_registry.py:6-27]
- **Evidence.** 23 modules across `core`, `extras`, `utilities` and `dcim` import `netbox.registry` directly. [fg:imports:core.management.commands.rqworker->netbox.registry] [fg:imports:extras.jobs->netbox.registry]

## ADR-4: Configuration is split into static settings and a database-backed dynamic layer

- **Context.** Operators deploy with a `configuration.py`, but some parameters (banners, pagination, maintenance mode, changelog retention) must be changeable at runtime without restart. [code:netbox/netbox/settings.py:44-63] [code:netbox/netbox/config/parameters.py:17-50]
- **Decision.** `settings.py` imports the module named by `NETBOX_CONFIGURATION`, validates required keys, and reads each parameter with `getattr(configuration, NAME, default)`; dynamic parameters are declared in `config/parameters.py`, stored as `core.ConfigRevision`, cached in Redis, and read through `get_config()`, a thread-local object that `CoreMiddleware` clears after every request; a value hard-coded in `settings.py` overrides the dynamic one. [code:netbox/netbox/settings.py:65-95] [code:netbox/netbox/config/__init__.py:42-67] [code:netbox/netbox/middleware.py:67-68]
- **Consequences.** Code must choose `settings.X` or `get_config().X` correctly per parameter; `Config` tolerates an unavailable database so management commands can run; `ConfigItem` exists to defer parameter lookups into callables. [code:netbox/netbox/config/__init__.py:76-93] [code:netbox/netbox/config/__init__.py:96-106] [code:netbox/netbox/api/pagination.py:13-14]
- **Evidence.** `settings.py` is the most-changed file in the codebase (960 commits, 52 authors since 2016); `config` has 24 importers. [fg:churn:netbox.settings] [fg:imports:core.signals->netbox.config]

## ADR-5: Bulk REST operations reuse the list endpoint via a custom router

- **Context.** Clients need to create, update and delete many objects per request; DRF's router only maps `POST` on list routes. [code:netbox/netbox/api/viewsets/mixins.py:77-94]
- **Decision.** `NetBoxRouter` remaps `PUT`/`PATCH`/`DELETE` on the list route to `bulk_update`/`bulk_partial_update`/`bulk_destroy`; bodies are lists validated by `BulkOperationSerializer`; `NetBoxModelViewSet.get_serializer` switches to `many=True` when given a list; each object is snapshotted and updated individually inside one transaction. [code:netbox/netbox/api/routers.py:4-18] [code:netbox/netbox/api/viewsets/mixins.py:98-131] [code:netbox/netbox/api/viewsets/__init__.py:129-134]
- **Consequences.** `BulkOperationMetadata` is required so OPTIONS describes the extra verbs; MPTT models need `MPTTLockedMixin` with a hand-registered advisory-lock key; `SequentialBulkCreatesMixin` exists for models whose validation depends on earlier creates in the same batch. [code:netbox/netbox/settings.py:684] [code:netbox/netbox/api/viewsets/__init__.py:214-230] [code:netbox/netbox/api/viewsets/mixins.py:53-74]
- **Evidence.** Ten app `api.views` modules import `netbox.api.viewsets`; `api.routers` has ten importers. [fg:imports:dcim.api.views->netbox.api.viewsets] [fg:imports:core.api.views->netbox.api.metadata]

## ADR-6: Change logging and event dispatch are request-scoped, via snapshots and ContextVars

- **Context.** Webhooks and event rules must fire once per committed change, with before/after data, and must not fire for rolled-back transactions. [code:netbox/netbox/models/features.py:91-113]
- **Decision.** `CoreMiddleware` assigns `request.id` and runs registered request processors in an `ExitStack`; `event_tracking` stores the request and an empty queue in `ContextVar`s, and flushes the queue after the response is produced; views call `obj.snapshot()` before mutation and `clear_events.send()` on abort. [code:netbox/netbox/middleware.py:33-45] [code:netbox/netbox/context_managers.py:8-28] [code:netbox/netbox/views/generic/object_views.py:272-274] [code:netbox/netbox/views/generic/object_views.py:336-339]
- **Consequences.** `request.id` is stored on `ObjectChange` and is queryable through `*_by_request` filters, which the bulk import view uses to redirect to "what I just imported"; anything mutating objects outside a request must manage the snapshot/queue itself. [code:netbox/netbox/filtersets.py:249-280] [code:netbox/netbox/views/generic/bulk_views.py:516-518] [code:netbox/netbox/tests/test_api.py:10-16]
- **Evidence.** `core.signals` reads `current_request` and `events_queue` from `netbox.context`. [fg:imports:core.signals->netbox.context] [fg:imports:netbox.context_managers->extras.events]

## ADR-7: The core/extras import cycle is tolerated and broken with lazy imports

- **Context.** The abstract base models need `CustomField`, `ObjectChange`, `DataFile`, `AutoSyncRecord` and `ContactAssignment`, all of which subclass those same base models. [fg:imports:netbox.models.features->extras.models] [fg:imports:extras.models.models->netbox.models]
- **Decision.** Module-level imports are limited to choices, constants and utilities; concrete models are imported inside the methods that use them, with an in-code TODO acknowledging the cycle. [code:netbox/netbox/models/features.py:13-23] [code:netbox/netbox/models/features.py:96-97] [code:netbox/netbox/models/features.py:380-383]
- **Consequences.** `netbox.models.features` is not importable without `core` and `extras` on the path; the same technique recurs in `config` (`ConfigRevision`) and in `register_models` (`register_model_view`), so the layering is "core package on top of apps" only at import time, not conceptually. [code:netbox/netbox/config/__init__.py:76-78] [code:netbox/netbox/models/features.py:651] [fg:imports:core.models.change_logging->netbox.models.features]

## ADR-8: Global search is a denormalised cache maintained by model signals

- **Context.** Searching across every model with weighted fields and custom fields cannot be done with per-model `icontains` queries alone. [code:netbox/netbox/search/__init__.py:30-44]
- **Decision.** Each model declares a `SearchIndex` (fields with weights) registered into `registry['search']`; the backend, chosen by `SEARCH_BACKEND`, is instantiated at import of `search.backends` and connected to global `post_save`/`post_delete` signals; the default backend writes `extras.CachedValue` rows in 2,000-row batches. [code:netbox/netbox/search/backends.py:273-290] [code:netbox/netbox/search/backends.py:187-239] [code:netbox/netbox/settings.py:172]
- **Consequences.** Every save of any model pays a handler call (unindexed models are skipped by `KeyError`); removal uses `_raw_delete()` to avoid loading instances; the `SearchView` and `SearchTable` in this package consume the backend directly. [code:netbox/netbox/search/backends.py:241-252] [code:netbox/netbox/views/misc.py:17-20] [fg:imports:netbox.search.backends->extras.models]
- **Evidence.** Ten app `search.py` modules import `netbox.search`; `search.backends` has 19 commits by 5 authors. [fg:imports:dcim.search->netbox.search] [fg:churn:netbox.search.backends]

## ADR-9: The GraphQL root schema is composed statically from every app

- **Context.** strawberry needs one `Query` type; apps and plugins each define their own. [code:netbox/netbox/graphql/schema.py:1-18]
- **Decision.** `netbox.graphql.schema.Query` inherits from the ten app `*Query` classes plus whatever is in `registry['plugins']['graphql_schemas']` at import time, with `auto_camel_case=False`, the Django optimizer and an alias limiter. [code:netbox/netbox/graphql/schema.py:20-44]
- **Consequences.** It is the only runtime module importing `circuits`, `ipam`, `virtualization`, `vpn` and `wireless`; plugin schemas must be registered before `netbox.urls` imports it; `GRAPHQL_ENABLED` and token auth live in the view. [fg:imports:netbox.graphql.schema->ipam.graphql.schema] [fg:imports:netbox.graphql.schema->vpn.graphql.schema] [code:netbox/netbox/graphql/views.py:13-43]
