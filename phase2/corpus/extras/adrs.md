# extras — retro-ADRs (NetBox ea4c205)

Decisions the code embodies that have no written record in the tree; each is stated as the code enforces it today, for the subsystem summarised in the fact graph. [fg:subsystems:extras]

## ADR-1: Custom-field values live in each object's JSONB column; `CustomField` is definition only

**Context.** Users must add fields to any model without a schema migration; every feature-bearing model already carries a `custom_field_data` JSON column via `CustomFieldsMixin`. [code:netbox/netbox/models/features.py:162-170] [fg:model_refs:extras.models.customfields:74]

**Decision.** `CustomField` rows describe type, validation and applicable `object_types`; values are stored under the field's name in the target rows' JSONB. Definition changes are propagated by signal handlers issuing server-side `jsonb_set`/key-deletion `UPDATE`s across every affected table; renames are detected by caching `_name` at `__init__`. [code:netbox/extras/models/customfields.py:281-328] [code:netbox/extras/signals.py:22-56] [code:netbox/extras/models/customfields.py:254-258]

**Consequences.** Typing is enforced in Python: `serialize`/`deserialize` for dates and object references, `validate` for regex/min/max/uniqueness, and a type switch repeated in `to_form_field` and `to_filter`; filtersets and serializers grow a field per CustomField at instantiation; removing a choice requires scanning every target table for its use; object-typed fields hold bare primary keys with no referential integrity. [code:netbox/extras/models/customfields.py:408-446] [code:netbox/extras/models/customfields.py:594-652] [code:netbox/netbox/filtersets.py:294-307] [code:netbox/extras/api/customfields.py:43-68] [code:netbox/extras/models/customfields.py:845-869]

## ADR-2: One polymorphic `EventRule` with a generic-FK action replaces per-webhook triggers

**Context.** Migration 0101 introduced `EventRule` and moved trigger data off `Webhook`; 0109 repointed script actions from `ScriptModule` to the new `Script` row; 0110 dropped `action_parameters`; 0120 replaced boolean type flags with an `event_types` array. [fg:model_refs:extras.migrations.0101_eventrule:11] [code:netbox/extras/migrations/0109_script_model.py:120-141] [fg:modules:extras.migrations.0110_remove_eventrule_action_parameters] [fg:modules:extras.migrations.0120_eventrule_event_types]

**Decision.** `EventRule` stores `event_types` (choices drawn from `registry['event_types']`), optional JSON `conditions` validated and evaluated by `ConditionSet`, an `action_type` choice, and an `action_object` GenericForeignKey. Dispatch is a hard-coded `if/elif` on `action_type` in `process_event_rules`, ending in `raise ValueError`. [code:netbox/extras/models/models.py:45-56] [code:netbox/extras/models/models.py:83-101] [code:netbox/extras/models/models.py:127-145] [code:netbox/extras/events.py:97-153]

**Consequences.** Adding an action kind touches `EventRuleActionChoices`, an `init_*_choice` method and the `clean()` branch of `EventRuleForm`, `process_event_rules`, and a reverse `GenericRelation` on the target model (Webhook, Script, ScriptModule, NotificationGroup each declare one). Webhook and Script actions are enqueued to RQ, while Notification actions write synchronously inside the flush. [code:netbox/extras/choices.py:242-252] [code:netbox/extras/forms/model_forms.py:488-522] [code:netbox/extras/forms/model_forms.py:536-563] [code:netbox/extras/models/models.py:228-232] [code:netbox/extras/models/scripts.py:45-49] [code:netbox/extras/models/notifications.py:147-152] [code:netbox/extras/events.py:140-148]

## ADR-3: Events are batched per request and flushed through a settings-defined pipeline

**Context.** Change logging in `core.signals` fires on every save/delete/m2m change; event consumers (webhooks, scripts, notifications) must not run inside the request transaction. [code:netbox/core/signals.py:13-14] [code:netbox/core/signals.py:45-58]

**Decision.** `enqueue_event` writes into a request-scoped dict keyed `app.model:pk`, collapsing repeated updates and upgrading update→delete; `event_tracking` (a registered request processor) flushes the dict at request end; `flush_events` calls each dotted path in `settings.EVENTS_PIPELINE`, logging rather than raising on failure. `process_event_queue` is the default consumer; webhooks are then re-queued to an RQ queue chosen via `QUEUE_MAPPINGS['webhook']`. [code:netbox/extras/events.py:53-81] [code:netbox/netbox/context_managers.py:8-28] [code:netbox/extras/events.py:186-196] [code:netbox/extras/events.py:156-183] [code:netbox/extras/events.py:98-124]

**Consequences.** Events only fire for models registered under the `event_rules` feature and only when a request is bound; script runs opt in by entering every registered request processor when `commit=True`; anything that must not emit events after a failure sends `clear_events`. The pipeline is pluggable, but the payload shape (`object_type`, `event_type`, `data`, `snapshots`, `username`, `request_id`) is an implicit contract with no schema. [code:netbox/extras/events.py:58-62] [code:netbox/extras/jobs.py:104-112] [code:netbox/extras/jobs.py:73-76] [code:netbox/extras/events.py:73-81]

## ADR-4: Scripts are database rows synced from file-backed modules, executed through a storage-aware loader; Reports are folded into Scripts

**Context.** Migration 0108 deleted the `Report` model and moved `ReportModule` jobs onto `ScriptModule`; 0109 created the `Script` table and rewrote jobs and event rules to reference it; 0129 repaired script paths. `Report` survives as a `BaseScript` subclass "required by 0109", and `BaseScript.run()` still calls `pre_run`/`run_tests`/`post_run` for legacy behaviour. [code:netbox/extras/migrations/0108_convert_reports_to_scripts.py:4-25] [code:netbox/extras/migrations/0109_script_model.py:80-118] [fg:modules:extras.migrations.0129_fix_script_paths] [code:netbox/extras/reports.py:9-34] [code:netbox/extras/scripts.py:440-448]

**Decision.** `ScriptModule` is a proxy over `core.ManagedFile` whose manager admits both SCRIPTS and REPORTS roots but whose `save()` forces SCRIPTS and then `sync_classes()`; `Script` rows are created/soft-deleted (`is_executable=False` when jobs exist) to mirror classes found by `inspect.getmembers(module, is_script)`. Module source is read from the `scripts` storage backend and `exec()`'d by `CustomStoragesLoader`; execution runs in `ScriptJob`, which lives outside the script class so authors cannot override it, wraps `run()` in `transaction.atomic()` and raises `AbortTransaction` when `commit` is false. [code:netbox/extras/models/scripts.py:87-113] [code:netbox/extras/models/scripts.py:154-193] [code:netbox/extras/models/scripts.py:78-84] [code:netbox/extras/models/mixins.py:21-35] [code:netbox/extras/jobs.py:16-25] [code:netbox/extras/jobs.py:40-52]

**Consequences.** Scripts are addressable by pk or `module.name` in UI, API and `runscript`; a script's identity is its module `file_path` plus class name; `ScriptFileForm.save` bypasses `ManagedFileForm.save` to write via storages; `ScriptFileSystemStorage` re-roots at `SCRIPTS_ROOT`; an RQ worker must be running or both UI and API refuse to enqueue; `load_yaml`/`load_json` are flagged for removal in v4.4. [code:netbox/extras/views.py:1292-1301] [code:netbox/extras/api/views.py:263-274] [code:netbox/extras/scripts.py:648-651] [code:netbox/extras/forms/scripts.py:62-77] [code:netbox/extras/storage.py:6-14] [code:netbox/extras/views.py:1347-1349] [code:netbox/extras/api/views.py:295-297] [code:netbox/extras/scripts.py:566-594]

## ADR-5: Config context is a weight-ordered deep merge with two deliberately parallel resolvers

**Context.** Devices and VMs need merged JSON from every applicable `ConfigContext`; list views and API list endpoints must do this for many objects at once. [code:netbox/extras/models/configs.py:26-31] [code:netbox/extras/querysets.py:73-81]

**Decision.** `ConfigContextQuerySet.get_for_object` resolves one object in Python (using MPTT `get_ancestors` for region, site group and role); `ConfigContextModelQuerySet.annotate_config_context_data` reproduces the same logic as a correlated subquery with tree-bounds comparisons and a `TaggedItem` subquery, aggregating with `EmptyGroupByJSONBAgg`. `ConfigContextModel.get_config_context()` uses the annotation when present, otherwise the per-object path, then `deepmerge`s `local_context_data` last. [code:netbox/extras/querysets.py:15-70] [code:netbox/extras/querysets.py:82-95] [code:netbox/extras/querysets.py:133-162] [code:netbox/extras/models/configs.py:173-194]

**Consequences.** Every qualifier exists in at least seven places: the `ConfigContext` M2M (declared with `related_name='+'` so dcim/virtualization get no reverse accessors), both resolvers, the filterset's id/slug pair, the model form, the serializer and the GraphQL type; device-only qualifiers are switched on `_meta.model_name`; the API omits the annotation for brief or `exclude=config_context` requests. [code:netbox/extras/models/configs.py:50-109] [code:netbox/extras/querysets.py:125-131] [code:netbox/extras/filtersets.py:593-603] [fg:imports:extras.api.serializers_.configcontexts->dcim.api.serializers_.sites] [code:netbox/extras/api/mixins.py:17-36]

## ADR-6: Models that leave extras keep their ContentType identity; UI state references code by string

**Context.** `ConfigRevision` (0102) and `ObjectChange` (0117) moved to `core`; the `Branch`/`StagedChange` experiment was removed (0124). [code:netbox/extras/migrations/0102_move_configrevision.py:4-33] [code:netbox/extras/migrations/0117_move_objectchange.py:4-25] [code:netbox/extras/migrations/0124_remove_staging.py:8-27]

**Decision.** Moves use `SeparateDatabaseAndState` to rename the table and then rewrite the existing `ContentType.app_label` in place, deleting the freshly created core row so generic FKs keep resolving. Dashboard layouts and widget configs are stored as JSON that names widget classes and models by label (`extras.NoteWidget`, `core.objectchange`), resolved at render time from `registry['widgets']`. [code:netbox/extras/migrations/0117_move_objectchange.py:17-25] [code:netbox/extras/models/dashboard.py:30-37] [code:netbox/extras/constants.py:25-32] [code:netbox/extras/dashboard/utils.py:29-36]

**Consequences.** extras remains the migration-history owner of models it no longer defines; any rename of a widget class or relocation of a model requires a data migration over every user's dashboard JSON (0115, 0117's `update_dashboard_widgets`), and an unregistered widget name raises `ValueError` at dashboard render. [fg:model_refs:extras.migrations.0115_convert_dashboard_widgets:5] [fg:model_refs:extras.migrations.0117_move_objectchange:17] [code:netbox/extras/dashboard/utils.py:29-36]
