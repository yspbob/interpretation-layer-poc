# users — retro-ADRs

## ADR-U1: Own the User and Group models instead of using `django.contrib.auth`

**Context.** Through NetBox 3.x the app stored users in Django's `auth_user` table and proxied `auth.Group` as `NetBoxGroup`; the squashed migrations still record `db_table: 'auth_user'` and M2Ms to `auth.group` [code:netbox/users/migrations/0001_squashed_0011.py:56-74] [code:netbox/users/migrations/0002_squashed_0004.py:47-62].

**Decision.** `AUTH_USER_MODEL` is `users.User`, an `AbstractUser` subclass whose `groups` M2M points at a home-grown `users.Group`; the stock `permissions` M2M to `auth.Permission` is retained on `Group` explicitly "to ensure authentication backend compatibility" [code:netbox/netbox/settings.py:521] [code:netbox/users/models/users.py:43-51] [code:netbox/users/models/users.py:74-81] [fg:model_refs:users.models.users:75].

**Consequences.** The move was done in place rather than by data copy: migration 0005 nulls `db_table`, widens `id` to bigint, renames sequences and indexes with raw SQL, and rewrites `ContentType` rows from `auth.user` to `users.user` so GenericForeignKeys keep resolving [code:netbox/users/migrations/0005_alter_user_table.py:31-51] [code:netbox/users/migrations/0005_alter_user_table.py:4-18]. Migration 0006 copies `auth_group` rows into `users_group` by SQL, repoints M2Ms, empties `auth_group` and `auth_group_permissions`, and fixes CustomField content types [code:netbox/users/migrations/0006_custom_group_model.py:26-72]. Both migrations were revised seven times through May 2025, the highest churn of any migration in the app [fg:churn:users.migrations.0005_alter_user_table] [fg:churn:users.migrations.0006_custom_group_model]. `User.clean` adds a case-insensitive uniqueness check that Django's model does not enforce [code:netbox/users/models/users.py:98-104].

## ADR-U2: Permissions are data rows (`ObjectPermission`), not `auth.Permission` codenames

**Context.** Django's permission system is per-model and boolean; NetBox needs per-object constraints and a variable set of actions [code:netbox/users/models/permissions.py:14-17].

**Decision.** `ObjectPermission` stores `actions` as a Postgres `ArrayField` of free strings, `constraints` as a JSON queryset filter (or list of filters, ORed), and `object_types` as an M2M to `core.ObjectType`; the authentication backend materializes `"{app}.{action}_{model}"` names from `object_types × actions` at check time [code:netbox/users/models/permissions.py:31-46] [code:netbox/netbox/authentication/__init__.py:94-107] [fg:model_refs:users.models.permissions:31]. The permission name grammar is fixed in `utilities.permissions.resolve_permission` as `<app>.<action>_<model>` [code:netbox/utilities/permissions.py:30-44].

**Consequences.** Five follow from storing actions as free strings and constraints as opaque JSON [code:netbox/users/models/permissions.py:35-44].
- Non-CRUD actions are legal and are used: the API checks `users.grant_token` before creating a token for another user, and tests grant it via `add_permissions('users.grant_token')`, while `ObjectPermission.Meta` declares no Django `permissions` for it [code:netbox/users/api/serializers_/tokens.py:46-54] [code:netbox/users/tests/test_api.py:279-300] [code:netbox/users/models/permissions.py:48-51]. The UI models the four CRUD actions as checkboxes and everything else as "Additional actions", reassembling the array in `clean` [code:netbox/users/forms/model_forms.py:282-299] [code:netbox/users/forms/model_forms.py:356-365].
- Constraints can only be validated by executing them: `ObjectPermissionForm.clean` runs `.filter(...).exists()` against each selected model with `$user` substituted by `0` and catches `FieldError`/`ValueError` [code:netbox/users/forms/model_forms.py:367-384] [code:netbox/users/constants.py:9].
- The `$user` token is a cross-subsystem contract: `users.constants` defines it, `utilities.querysets.restrict` and `utilities.permissions.qs_filter_from_constraints` substitute it, the latter resolving `users.User` lazily via `apps.get_model` to avoid a circular import [fg:imports:utilities.querysets->users.constants] [code:netbox/utilities/permissions.py:85-99] [fg:model_refs:utilities.permissions:96].
- Which models may be targeted is a Q expression in `constants.py` that excludes Django internals but allowlists the four public `users` models [code:netbox/users/constants.py:4-7].
- Filtering permissions by capability requires array-containment queries (`actions__contains=[action]`) rather than joins [code:netbox/users/filtersets.py:206-211].

## ADR-U3: Permission assignment M2Ms live on User and Group, not on ObjectPermission

**Context.** The original schema put `groups` and `users` M2Ms on `ObjectPermission` [code:netbox/users/migrations/0001_squashed_0011.py:119-143].

**Decision.** Migration 0008 flips ownership: `Group.object_permissions` and `User.object_permissions` are the declared fields, with `related_name='groups'`/`'users'` so the reverse accessors keep their old names [code:netbox/users/models/users.py:37-41] [code:netbox/users/models/users.py:82-86] [fg:model_refs:users.models.users:37] [fg:model_refs:users.models.users:82].

**Consequences.** The flip used `SeparateDatabaseAndState` and renamed the through tables, sequences, constraints and indexes by SQL so existing assignments survived; one constraint is dropped-if-exists and recreated because of a known inconsistency (#15698) [code:netbox/users/migrations/0008_flip_objectpermission_assignments.py:11-48]. The backend's filter `Q(users=user_obj) | Q(groups__user=user_obj)` and the API's `users`/`groups` fields on the permission serializer were unaffected because the reverse names were preserved [code:netbox/netbox/authentication/__init__.py:75-76] [code:netbox/users/api/serializers_/permissions.py:19-31]. On the User/Group API the field is still called `permissions`, aliased to `object_permissions` via `source=` [code:netbox/users/api/serializers_/users.py:19-26]. Forms for Group and ObjectPermission must sync the non-owning side by hand with `.set()` [code:netbox/users/forms/model_forms.py:266-272] [code:netbox/users/forms/model_forms.py:386-393].

## ADR-U4: API tokens are first-class, many-per-user, self-provisionable, and hidden after creation by default

**Context.** DRF's stock token is one-per-user with no expiry or scoping [code:netbox/users/models/tokens.py:22-25].

**Decision.** `Token` is NetBox's own model with `expires`, `last_used`, `write_enabled`, `allowed_ips` and an auto-generated 160-bit key; `TokenAuthentication` in `netbox.api` enforces expiry and source IP and throttles `last_used` writes to once a minute [code:netbox/users/models/tokens.py:26-72] [code:netbox/netbox/api/authentication.py:13-59]. A user may obtain a token by POSTing credentials to an unauthenticated endpoint (`permission_classes = []`) that authenticates via `django.contrib.auth.authenticate` [code:netbox/users/api/views.py:55-72] [code:netbox/users/api/serializers_/tokens.py:82-93]. Key visibility is governed by `ALLOW_TOKEN_RETRIEVAL` (default `False`) [code:netbox/netbox/settings.py:67].

**Consequences.** Every layer that could reveal a key re-checks the setting (model `__str__`, serializer `write_only`, form field removal), and every creation path regenerates a missing key independently [code:netbox/users/models/tokens.py:78-96] [code:netbox/users/api/serializers_/tokens.py:17-44] [code:netbox/users/forms/model_forms.py:141-150]. Creating a token for someone else is a distinct capability (`grant_token`) from `add_token` [code:netbox/users/api/serializers_/tokens.py:46-54]. Self-service is delegated to the `account` app through a `_netbox_private` proxy model `UserToken`, whose table the admin-side `TokenTable` then inherits [code:netbox/account/models.py:6-17] [code:netbox/users/tables.py:16-27].

## ADR-U5: User preferences are a schemaless JSON document, seeded by signal and merged without validation

**Context.** Preferences are heterogeneous (UI, pagination, per-table column/ordering state, plugin settings) and grow without migrations [code:netbox/users/forms/model_forms.py:59-66] [code:netbox/users/forms/model_forms.py:104-108].

**Decision.** `UserConfig.data` is a `JSONField` navigated by dotted paths; `get()` falls back to `config.DEFAULT_USER_PREFERENCES`; a `post_save` signal creates the row for every new user with those defaults (skipping fixture loads) [code:netbox/users/models/preferences.py:32-63] [code:netbox/users/signals.py:26-32]. The set of *editable* preferences is a registry, `netbox.preferences.PREFERENCES`, built from `users.preferences.UserPreference`, and `UserConfigForm`'s metaclass synthesizes one `TypedChoiceField` per entry at class-creation time [code:netbox/users/preferences.py:1-11] [fg:imports:netbox.preferences->users.preferences] [code:netbox/users/forms/model_forms.py:32-55].

**Consequences.** The REST endpoint `/api/users/config/` is a bare `ViewSet` scoped to `request.user` that `deepmerge`s arbitrary JSON into the document; the code carries a `TODO: How can we validate this data?` [code:netbox/users/api/views.py:95-123]. `set()` refuses to overwrite a branch with a leaf or vice versa, which is the only structural guard [code:netbox/users/models/preferences.py:86-112]. Table state is written by `NetBoxTable.configure`, so `test_preferences` depends on `dcim` to exercise it [code:netbox/users/tests/test_preferences.py:47-63] [fg:imports:users.tests.test_preferences->dcim.tables]. `account.views` defensively recreates a missing `UserConfig` because the signal is the only other creator [code:netbox/account/views.py:120-124].

## ADR-U6: Auth models are deliberately outside the `NetBoxModel` feature set

**Context.** `NetBoxModel` brings change logging, custom fields, tags, journaling and GraphQL registration to ordinary NetBox objects [code:netbox/netbox/models/features.py:641-660].

**Decision.** `User`, `Group`, `ObjectPermission` and `Token` are plain `models.Model`/`AbstractUser` subclasses registered via `register_models` but carrying none of the feature mixins; `UserConfig` is additionally `_netbox_private` [code:netbox/users/models/users.py:26] [code:netbox/users/models/permissions.py:13] [code:netbox/users/models/tokens.py:21] [code:netbox/users/models/preferences.py:25] [code:netbox/users/apps.py:7-12].

**Consequences.** The user detail page shows changes made *by* the user (`ObjectChange.filter(user=instance)`), not changes *to* the user, since none are recorded [code:netbox/users/views.py:73-85]. Only `User` and `Group` have GraphQL types; Token and ObjectPermission have none, and the API test suite skips the GraphQL mixin for Token with an explicit comment [code:netbox/users/graphql/schema.py:9-15] [code:netbox/users/tests/test_api.py:191-198]. All four public models are listed in `EXEMPT_EXCLUDE_MODELS`, so `EXEMPT_VIEW_PERMISSIONS = ['*']` never exposes them [code:netbox/netbox/settings.py:569-578]. Group/User counts must be annotated per view (`users_count` in the UI, `user_count` in the API) because there is no cached counter field [code:netbox/users/views.py:125-131] [code:netbox/users/api/views.py:39-42].
