# core — subsystem map (NetBox @ ea4c205)

## What it is

`core` is the Django app that owns NetBox's cross-cutting runtime records: the change log (`ObjectChange`), the background-job ledger (`Job`), remote data synchronisation (`DataSource`, `DataFile`, `AutoSyncRecord`), disk-backed files (`ManagedFile`), dynamic configuration (`ConfigRevision`), and the `ObjectType` proxy over Django's `ContentType`. It is 68 modules and 7,152 lines of code with six test modules [fg:subsystems:core] [code:netbox/core/models/__init__.py:1-6].

It is also the app that hooks the framework: `CoreConfig.ready()` registers every core model with the feature registry, registers the seven built-in event types, and imports the schema fixes, system checks, data backends and search indexes so their decorators run [code:netbox/core/apps.py:23-40]. At module import time `apps.py` also patches Django itself, removing `verbose_name` from migration-relevant options and replacing `Field.deconstruct` [code:netbox/core/apps.py:12-17].

## Modules by role

**Models** are split per concern and re-exported by the package `__init__` [code:netbox/core/models/__init__.py:1-6].
- `contenttypes`: `ObjectType`, a proxy of `ContentType` whose manager filters by `registry['models']` and `registry['model_features']` [fg:symbols:core.models.contenttypes:ObjectType] [code:netbox/core/models/contenttypes.py:12-50].
- `change_logging`: `ObjectChange` with two GenericForeignKeys (changed and related object), diff helpers, and a `valid_models()` queryset that drops rows for uninstalled models [fg:symbols:core.models.change_logging:ObjectChange] [code:netbox/core/querysets.py:12-26].
- `data`: `DataSource` (a `PrimaryModel` with `JobsMixin`), `DataFile` (plain model, binary `data`), `AutoSyncRecord` (private GFK map) [fg:symbols:core.models.data:DataSource] [code:netbox/core/models/data.py:263-301] [code:netbox/core/models/data.py:358-378].
- `jobs`: `Job`, a plain model that mirrors an RQ job by UUID and enqueues on commit [fg:symbols:core.models.jobs:Job] [code:netbox/core/models/jobs.py:208-244] [code:netbox/core/models/jobs.py:245-273].
- `files`: `ManagedFile`, a private `SyncedDataMixin` model for scripts/reports on disk [fg:symbols:core.models.files:ManagedFile] [code:netbox/core/models/files.py:24-51].
- `config`: `ConfigRevision`, whose `activate()` writes into the Django cache [fg:symbols:core.models.config:ConfigRevision] [code:netbox/core/models/config.py:56-66].

**Views** (`core.views`, 38 classes, 649 LOC): generic CRUD views for the five DB-backed models registered via `register_model_view`, plus raw-RQ views (`BaseRQView` family), `SystemView`, and the plugin catalog views [fg:modules:core.views] [code:netbox/core/views.py:47-58] [code:netbox/core/views.py:343-347] [code:netbox/core/views.py:526-529] [code:netbox/core/views.py:589-593].

**Forms**: `model_forms` (DataSource with dynamic backend fields, ManagedFile, ConfigRevision with a metaclass that emits one field per config `PARAM`), `bulk_edit`, `bulk_import`, `filtersets`, and `mixins.SyncedDataMixin`, which other apps reuse [fg:symbols:core.forms.model_forms:ConfigFormMetaclass] [code:netbox/core/forms/model_forms.py:127-146] [fg:imports:extras.forms.model_forms->core.forms.mixins].

**Tables**: one module per model plus `columns` (`BackendTypeColumn`, `RQJobStatusColumn`), `tasks` (RQ queue/task/worker tables on `BaseTable`), `plugins` and `template_code` [fg:symbols:core.tables.columns:BackendTypeColumn] [fg:symbols:core.tables.tasks:BackgroundQueueTable] [code:netbox/core/tables/__init__.py:1-6].

**Filtersets**: five classes; `DataSourceFilterSet` is a `NetBoxModelFilterSet`, `DataFileFilterSet` a `ChangeLoggedModelFilterSet`, the rest `BaseFilterSet` [fg:symbols:core.filtersets:DataSourceFilterSet] [fg:symbols:core.filtersets:JobFilterSet] [code:netbox/core/filtersets.py:23-24] [code:netbox/core/filtersets.py:78].

## Entry points

UI URLs are mounted at `core/` and API URLs at `api/core/` from the project router [code:netbox/netbox/urls.py:27] [code:netbox/netbox/urls.py:46]. Model URLs come from `get_model_urls('core', <model>)`; RQ, system and plugin views are wired with explicit `path()` entries [fg:entrypoints:core.urls] [code:netbox/core/urls.py:9-19] [code:netbox/core/urls.py:22-54]. The REST router registers `data-sources`, `data-files`, `jobs`, `object-changes` and three RQ basenames [fg:entrypoints:core.api.urls] [code:netbox/core/api/urls.py:9-15]. Signal receivers are an entry point in their own right: they fire on every `post_save`, `m2m_changed` and `pre_delete` in the process [fg:entrypoints:core.signals] [code:netbox/core/signals.py:45-46] [code:netbox/core/signals.py:111-112].
